Fixes and adjustments on top of 100-transcoding-2117.patch.
101 and 102 are ported from PR #2133; 103 is cosmetic; 104 and 105 repair
a regression introduced by the profile rework in PR #2117.

Both address rows that were not green in the 2026-08-09 test table:
  https://github.com/tvheadend/tvheadend/pull/2117#issuecomment-5232768590

101-transcode-hwaccel-decode-fallback.patch
  Fixes: "webm | vp9 | vorbis | vaapi -> video: Unsupported, audio also lost"

  hwaccels_decode_get_format() returns a software pixel format when no
  hardware format can be set up (a VAAPI device with no VP9 decode entrypoint
  is the common case), but leaves ctx->iavhwdevtype at AV_HWDEVICE_TYPE_VAAPI.
  The filter graph is then still built for hardware frames, graph
  configuration fails, and the whole subscription dies instead of degrading
  to audio only.  Clear the hardware intent at that point.

  Upstream equivalent: same block exists in PR #2133.

102-transcode-apply-stream-params.patch
  Fixes: "Matroska/MP4 | HEVC | aac | no (software) -> lagging + artifacts"
  (the lag is CPU-bound and expected; the artifacts are not)

  The buffer filter source is configured straight from self->iavctx
  (video_size, pixel_aspect) and, on the filter2 path, from par->width /
  par->height / par->frame_rate.  Nothing ever fills those fields from what
  the parser already resolved: stream.c copies es_sample_aspect_ratio only,
  and only inside #if ENABLE_MMAL|V4L2M2M|NVENC|VAAPI|QSV -- width, height
  and frame rate are never applied.

  Symptom chain:
    "AVCodecContext: Invalid frame dimensions 0x0."   (geometry unset)
      -> frames leave the graph with no usable duration
      -> the rescale falls back on oavctx->framerate, also unset
      -> the pts monotonicity guard in tvh_video_context_encode() fires:
         "Invalid pts (N) <= last (M), dropping frame"
      -> dropped frames on a software encoder == visible artifacts

  Hardware paths largely negotiate geometry from the frames context, which is
  why only the software rows show the damage.

  Ports tvh_video_apply_stream_params() from PR #2133:
    - elementary_info_t es_info snapshot in TVHContext  (internals.h)
    - memcpy of ssc into it at transcode setup          (stream.c)
      deliberately OUTSIDE the hwaccel #if: a software-only build needs it too
    - helper called at decoder open and again before the buffer source is
      built                                             (video.c)

  The memcpy is safe because struct streaming_start_component embeds
  elementary_info_t as an anonymous member at offset 0 (src/esstream.h).

103-transcode-rename-matroska-to-mkv.patch
  Cosmetic: the 6 Matroska stream profiles are renamed from "...-aac-matroska"
  to "...-aac-mkv", so the container segment is short like the mp4 and webm
  ones already are.  The "comment" fields deliberately keep the long spelling
  ("WEBTV profile H264 QSV/AAC/Matroska"), which is what the UI shows.

104-transcode-restore-mpegts-profile.patch
  Restores the MPEG-TS profile the profile rework in PR #2117 dropped.

  Upstream master ships webtv-h264-aac-mpegts (container 2 = MC_MPEGTS).  The
  rework replaced the four upstream profiles with sixteen covering webm,
  matroska and mp4 only -- no MPEG-TS survives.  This re-adds a single
  software profile, matching upstream parity and the new naming:
  webtv-h264-software-aac-mpegts.

  Needed by 105: three of the web TV player's five playback modes use it.

105-transcode-fix-webui-tv-profiles.patch
  src/webui/static/tv.js hardcodes the profile name for each playback mode.
  The profile rework renamed or removed every one of them, so all five modes
  referenced profiles that no longer exist:

    webm   webtv-vp8-vorbis-webm    -> webtv-vp8-software-vorbis-webm
    hls    webtv-h264-aac-mpegts    -> webtv-h264-software-aac-mpegts
    apple  webtv-h264-aac-mpegts    -> webtv-h264-software-aac-mpegts
    ts     webtv-h264-aac-mpegts    -> webtv-h264-software-aac-mpegts
    mkv    webtv-h264-aac-matroska  -> webtv-h264-software-aac-mkv

  ('pass' is a built-in profile and is not affected.)

  Apply order matters: 103 provides the -mkv name, 104 provides the mpegts
  profile.  This is a regression of PR #2117 itself and should be reported
  upstream rather than carried here indefinitely.

Notes
  - 101+102 are purely additive: +74 / -0 across 4 files.
  - Deliberately avoid the design points uknunknown set aside in #2133:
    no combined VAAPI/QSV/NVENC filters, no drmdev relocation, no
    has_support_for_filter2.
  - Verified to apply with `patch -p0` both on the tree produced by the
    current 100-transcoding-2117.patch and on the current head of PR #2117,
    so they survive a regeneration of the 100- patch.
  - Uses av_reduce() (already used in video.c) rather than av_gcd(), which
    that translation unit does not otherwise pull in.
