Patches applied on top of 100-transcoding-2117.patch (PR #2117).

Several of these were written for a cause that later turned out to be wrong.
The classification below reflects what each patch is now known to do, verified
on a Synology DS918+ (Celeron J3455), 1280x720 MPEG-2 source at 59.94 fps
scaled to 384p.

=============================================================================
ESSENTIAL -- regressions introduced by PR #2117
=============================================================================

104-transcode-restore-mpegts-profile.patch
    The profile rework in #2117 dropped webtv-h264-aac-mpegts entirely
    (upstream master ships it, container 2 = MC_MPEGTS). Re-adds one software
    profile at upstream parity. Required by 105.

105-transcode-fix-webui-tv-profiles.patch
    src/webui/static/tv.js hardcodes a profile name per playback mode. The
    rework renamed or removed every one of them, so all five modes of the web
    TV player (webm, hls, apple, ts, mkv) pointed at profiles that no longer
    exist -- three of them with nothing to point at.

108-muxer-libav-fix-false-reconfigure.patch
    #2117 rewrote lav_muxer_reconfigure() from "return -1" (master and #2133)
    into a loop that does nothing and returns 0. The libav muxer cannot be
    reconfigured -- avformat_write_header() has already emitted ftyp/moov --
    so claiming success left the muxer with stale state and silenced the
    caller's "Unable to reconfigure stream" warning.

    NOTE: this restores honest reporting, nothing more. It was first believed
    to fix the malformed-MP4 problem; it does not. That is 109.

=============================================================================
ESSENTIAL -- pre-existing upstream bug, not introduced by #2117
=============================================================================

109-muxer-libav-avio-buffer-size.patch
    MUX_BUF_SIZE was 4096 (same in master and #2133). libavformat writes each
    box with a placeholder size and seeks back to patch it; on a non-seekable
    output that only works while the target byte is still in the unflushed
    buffer. An HEVC moov straddled 4096, so the seek failed silently and the
    moov kept size 0 -- an unparseable file, no video and no audio.

        libx265    global header 2449 -> hvcC 2477, moov 4022..5078
        hevc_qsv   global header  104 -> hvcC  120, moov 1657..2421
        libx264    global header   40 -> avcC   43, moov 1568..2328

    Only libx265 came near the limit: x265 embeds a verbose SEI (its full
    option string) in the global header. Fresh clients were a coin toss around
    the threshold; a client joining a running transcode produced a 5078-byte
    moov and therefore failed every time.

    Raised to 32768 -- about six times the worst case observed, at 32k per
    active libav-muxed client (against the 50 MB input queue tvheadend already
    allocates per mpegts input).

    Verified after the change: 6/6 fresh clients valid, late joiners 5078,
    5078, 5062; h264 and qsv unchanged.

    Worth reporting upstream: this affects any MP4 whose header exceeds 4 KB,
    well beyond this PR. The 2449-byte x265 global header is a second, separate
    avenue -- excluding that SEI from the hvcC would have kept the moov near
    2600 and 4096 would have sufficed.

=============================================================================
ESSENTIAL on low-end hardware -- makes a shipped profile usable at all
=============================================================================

106-transcode-hevc-software-preset.patch
    webtv-hevc ships preset=faster tune=zerolatency. libx265 cannot sustain
    realtime here, and the failure mode is silent: the mpegts input queue
    passes 50 MB, mpegts_input_queue_packets() discards raw TS packets, and the
    decoder reports "concealing NNNN DC/AC/MV errors" -- visible artifacts,
    with no message naming the transcode or the profile.

    Full matrix measured: 5 presets x 7 tunes. Exactly one combination sustains
    realtime -- preset=ultrafast tune=fastdecode. fastdecode is also the
    libx265 class default (.def.s in libx26x.c); the shipped JSON overrides it
    with zerolatency, the worst of the seven (it forces frame-threads=1).

    Side effect, measured: also removes the web UI freeze. The sharer thread
    holds prsh_queue_mutex across each encode while profile_chain_close() waits
    for it under global_lock, and profile_input_queue() is unbounded, so a
    backlog starves the lock. /api/channel/grid (which needs global_lock) went
    from 0.7 ms idle to 20 s during software HEVC; afterwards the worst sample
    is 3.1 s with no timeouts. The lock design itself is untouched and will
    bite again on slower hardware or heavier sources.

    NOTE: ultrafast is a heavy quality trade-off chosen for this hardware
    class. It is not obviously the right upstream default.

=============================================================================
USEFUL -- real fixes, for scenarios not reachable on this hardware
=============================================================================

101-transcode-hwaccel-decode-fallback.patch    (ported from PR #2133)
    From #2133 commit 9798a7112: when the hardware device is unusable at
    runtime (missing or broken /dev/dri, driver init failure), get_format()
    falls back to a software pixel format but iavhwdevtype keeps its hardware
    value, so the filter chain is still built hardware-only,
    avfilter_graph_config() fails and the stream is stopped -- where a software
    transcode used to take over.

    Relevant to Synology models without an iGPU or with /dev/dri permission
    problems. NOT triggered where VAAPI works, and NOT the cause of the
    VP9/VAAPI failure (that one is the encoder, not the decoder).

102-transcode-apply-stream-params.patch        (ported from PR #2133)
    From #2133 commit ff58ba046: carries width/height, sample aspect ratio and
    frame rate from the parser's elementary-stream info into the decoder
    context, which is what the buffer filter source is configured from.

    Observed effect: removes the "AVCodecContext: Invalid frame dimensions
    0x0." flood. Its stated purpose upstream is correct aspect ratio (this
    source carries SAR 1024/1023). NOT the cause of the artifacts -- those are
    the input loss described under 106.

=============================================================================
OPTIONAL
=============================================================================

103-transcode-rename-matroska-to-mkv.patch
    Cosmetic. Renames the six Matroska stream profiles from "...-aac-matroska"
    to "...-aac-mkv" so the container segment is short like mp4 and webm
    already are. The "comment" fields keep the long spelling, which is what the
    UI displays. 105 references the -mkv name, so the two go together.

107-muxer-libav-report-avcc-hvcc-failure.patch
    Diagnostic only, no behaviour change. isom_write_avcc()/isom_write_hvcc()
    had their return value discarded, so a failed conversion left a track with
    empty extradata and no message anywhere. Reports that, the separate case of
    a track needing a codec configuration but having no global header, and
    traces the sizes on success.

    It is what produced the global-header figures quoted under 109, and its
    silence is what ruled out the transcode layer and moved the search to the
    muxer. Keep it: the sizes it traces are the only visibility into how close
    a given codec runs to the buffer limit.

Apply order
=============================================================================
    100 -> 101 -> 102 -> 103 -> 104 -> 105 -> 106 -> 107 -> 108 -> 109
    105 needs the -mkv name from 103 and the mpegts profile from 104.
    The rest are independent.

Resolved along the way
    VP9/VAAPI: the Gen9 iGPU has no VP9 encode entrypoint, so OPEN_ENCODER
    fails. #2117 advertised the video track anyway and the muxer then waited
    for frames that never came, so the audio never shipped either -- 3,509
    bytes in 20 s, with the WebM header declaring both V_VP9 and A_VORBIS.

    After 108 and 109 the same profile degrades to audio only, which is what
    #2133 did: 384,598 bytes in 20 s and a header declaring A_VORBIS alone
    (against 4,599,415 bytes and V_VP8 + A_VORBIS for the working vp8 profile).
    Not attributed to either patch individually -- no measurement was taken
    between them -- but the result is reproducible.
